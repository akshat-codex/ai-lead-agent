Industry taxonomy matching — the critical question

Can the system return companies that merely mention an ICP industry rather than belong to it? Yes, at the third tier — and the code says so itself.

Tier 1 & 2 — exact match only

explorium.py:386, _lookup_categoryif isinstance(label, str) and isinstance(value, str) and clean_text(label).casefold() == cleaned:
    matched = value
    break

Full-string, case/whitespace-normalized equality against the autocomplete label — never a "closest suggestion." No fuzzy or semantic broadening exists here. Confirmed by a dedicated test, test_naics_never_fuzzy_matches_a_near_miss_label.

Tier 3 — keyword fallback, self-documented as low precision

explorium.py:38-51, module docstringwebsite_keywords alone is low-precision: it matches any word appearing
anywhere on a company's website, so a recruiting agency whose site merely
mentions "Healthcare" surfaces as readily as a real healthcare company
(confirmed live: a website_keywords=[Healthcare] sample returned 0/10
genuinely healthcare companies).
explorium.py:699keyword["website_keywords"] = {"values": all_keyword_terms, "operator": "or"}

Confirmed, not inferred

The engineering team that wrote this adapter already live-tested the failure mode and left the result in the docstring: a healthcare keyword search returned 0 of 10 genuinely healthcare companies. This is a known, accepted precision gap for any industry term that misses both structured taxonomies.

Downstream mitigation — but not elimination

The hard-rule industry check (hard_rule_engine.py::_evaluate_choice_field:222-250) uses strict exact-string equality, not substring matching — so a keyword-discovered company whose evidence industry field doesn't exactly match an allowed term will FAIL or HOLD downstream. This limits — but does not prevent — wasted discovery slots and candidate-pool pollution from the keyword tier, since the company still consumed a discovery slot and a full evidence/qualification pass.

explorium.py:270-275 — overlap semantics, not containmentselected = [
    label
    for label, bucket_lo, bucket_hi in buckets
    if (bucket_hi is None or bucket_hi >= lo) and (hi is None or bucket_lo <= hi)
]
  • Discovery-time, provider-side filter — company_size is sent as an Explorium API filter, not applied client-side after the fact.
  • Overlap, not containment — deliberate design (documented at explorium.py:70-83) fixing a prior bug where a non-bucket-aligned range like 15–150 produced no filter at all and silently admitted IBM/Meta/Deloitte (10001+ employees).
  • Consequence: a real 180-employee company can be admitted against a 15–150 ICP request, because 180 falls in the overlapping 51–200 bucket. This is explicitly acknowledged in code as intentional — "never silently drop the constraint entirely."
  • Malformed range (min>max) sends no filter at all — unconstrained discovery for that request.
  • employee_count and employee_range are kept fully distinct at every layer (schemas/candidate.py:24-29). Explorium supplies only the string range — this adapter has no mapping that produces a precise integer count.
  • Hard-rule stage prefers exact count when present, else re-applies the same overlap test used at discovery — for "consistency," per the code comment. Missing both → HOLD (EMPLOYEE_COUNT_UNKNOWN).

Is employee size a discovery filter, a qualification rule, or both? Both — and both stages independently apply overlap logic, so they can agree or disagree depending on what evidence is actually available for a given candidate.

Confidence for every discovery-derived record is always ConfidenceLevel.UNKNOWN — never invented. Status derivation:

evidence_engine.py:154-167if len(distinct_values) > 1: return CONFLICT

Only industry and country are in _TRUSTED_STRUCTURED_FIELDS, and only explorium-company-discovery-v1 is a trusted structured provider (evidence_engine.py:108,116). A single Explorium sighting of industry or country can therefore gate a hard rule on its own — but a single sighting of employee_range, company_type, or domain cannot, unless corroborated by a second source.

Coverage gap, not data loss

company_type and business_model are both declared critical evidence fields (evidence_engine.py:66-85), but Explorium supplies neither — _BUSINESS_ATTRIBUTE_MAP has no mapping for either. They stay UNKNOWN from discovery evidence alone, and the corresponding hard rules default to HOLD, pending a separate classification pipeline (business_model_classifier.py, out of this audit's scope).

Hard-rule qualification

hard_rule_engine.py:361-369failed = tuple(r for r in rule_results if r.status == RuleStatus.FAIL)
unresolved = tuple(r for r in rule_results if r.status == RuleStatus.HOLD)
if failed: overall = FAIL
elif unresolved: overall = HOLD
else: overall = PASS

FAIL always outranks HOLD; PASS requires zero FAILs and zero HOLDs. Missing-data behavior is uniform and conservative — unknown employee/geography/industry/title/company_type all resolve to HOLD, never a guessed PASS. A hard-rule field is only ever populated on a candidate when its evidence status is SUPPORTED or SUPPORTED_STRUCTURED (hard_icp_validation.py:42,45-60); anything else leaves the field None, which the engine then treats as missing.

Are discovery filters and hard rules separate stages? Yes, and this is architecturally enforced — company_discovery.py's own module docstring states it "knows nothing about qualification" and never imports the hard-rule engine (confirmed: no such import exists in either company_discovery.py or explorium.py). They can still disagree in outcome by design: discovery's bucket-overlap employee filter can admit a company whose exact count later fails the hard rule's stricter numeric check. The code frames this explicitly — the discovery filter's "only job is to keep discovery from returning wildly oversized/undersized companies... not to be the final authority on fit."

9

Candidate pool assembly

  • Requested count — batch.discovery_limit (default 20, range 1–100), passed through to Explorium's adapter which further caps page_size at 100.
  • Pagination — cursor-based, per-provider, per-branch; auto-continuation capped client-side at 20 rounds, counting only ACCEPTED outcomes toward target, never padding with HELD/REJECTED items.
  • Dedup keys — within one Explorium call: business_id across branches. Within one provider response: external_id. Across rounds: (provider_id, external_id), checked before creating new batch items.
  • FAIL / HOLD / REJECTED / DUPLICATE candidates all reach the frontend — lead_ranking.py returns every tier, not PASS-only, and CompanyRankingList renders them all. This is intentional, per the ranking module's own docstring.
  • Could provider limits hide good companies? Plausibly — page size is split across up to 3 active branches per round, and a non-retryable Explorium error (auth/credits) halts all further rounds immediately. The orchestration layer explicitly documents this as accepted behavior: "under-delivery is expected, never forced."

Currently working

  • The live batch pipeline is coherent end to end — discovery, resolution, evidence import, hard-rule validation, scoring, LLM qualification, dedup, and ranking all run in a documented, testable sequence with no missing links in the happy path.
  • Discovery and qualification are genuinely decoupled, verified by absence of hard-rule imports in the discovery modules — not just a claim in a comment.
  • Employee-bucket filtering is provider-side and non-trivial — it was clearly hardened after a real production bug (IBM/Meta-class companies leaking through on malformed ranges) and now has explicit regression tests guarding against silent filter loss.
  • Evidence confidence is honest — nothing from discovery is ever marked HIGH/MEDIUM confidence; the system only trusts a single sighting for two specifically named, narrow, high-precision fields (industry, country) from one specifically named trusted provider.
  • Cross-round, cross-branch, and cross-provider dedup all exist and are keyed correctly (business_id → external_id → provider_id+external_id).
  • Test coverage on the core engines is genuinely thorough — test_hard_rule_engine.py (48 tests) and test_explorium_provider.py (63 tests) cover edge cases like bucket-boundary overlap, malformed strings, FAIL-beats-HOLD priority, and NAICS never-fuzzy-matching.

"Can this current discovery system reliably produce high-quality companies for arbitrary real-world ICPs?"

For ICPs whose industry and geography terms exist as exact labels in Explorium's linkedin_category or NAICS taxonomies, yes — the structured path is exact-match, provider-side filtered, and backed by a genuinely conservative, well-tested hard-rule layer that defaults to HOLD rather than guessing.

For arbitrary real-world ICPs — where industry phrasing is a user's own words, not a taxonomy label — no, not reliably. The system's own code documents a measured 0/10 precision result for the keyword-fallback tier that any unmatched term falls into. Nothing in the architecture currently distinguishes "no taxonomy match, treat this cautiously" from "no taxonomy match, search everywhere anyway" — it always does the latter.

The qualification layer is a real safety net, not decoration — it will HOLD or FAIL a poorly-matched company rather than pass it silently. But candidates that never should have entered discovery still consume a slot, an evidence pass, and (per the pipeline trace) an LLM qualification call before that net catches them, which is a cost and latency problem even when it's not a correctness problem.

G

Top 5 problems that must be solved

  1. 1

    Industry keyword fallback has no precision safeguard

    Any ICP term missing from both linkedin_category and NAICS falls into a self-documented low-precision substring search. This is the single highest-leverage fix for lead quality — everything downstream (evidence, hard rules, LLM qualification) is spending real cost cleaning up after it.

  2. 2

    Six ICP fields are UI-visible but functionally inert

    Funding, hiring, technology, revenue, website, and (for filter-builder purposes) growth_signals give users the impression of control they don't actually have over discovery or scoring.

  3. 3

    No structured evidence source for company_type or business_model

    Both are declared critical fields with zero Explorium mapping — every discovery-only candidate HOLDs on these until a separate classifier fills the gap, which the audit didn't trace.

  4. 4

    Unrecognized geography terms silently vanish at discovery time

    No visible signal to the user that "Nordics" or "EMEA" contributed nothing to the actual provider filter.

  5. 5

    Dead frontend pipeline remains in the codebase

    Low current risk, but a real regression trap for future refactors — worth deleting outright rather than leaving as an attractive nuisance.
