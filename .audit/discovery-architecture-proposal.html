Current weaknesses — bugs vs. architectural limitations

Keyword fallback is a self-documented substring match, not a category match

High · Architectural limitation
providers/explorium.py:38-51, :699

Any ICP industry term without an exact LinkedIn-category or NAICS label falls into website_keywords, which Explorium matches against any word appearing anywhere on a site. The adapter's own docstring records a live test where this returned 0/10 genuinely-matching companies for "Healthcare." This is the direct mechanism behind the D2C/FMCG problem (Section 6).

Not a bug — the precedence order (structured tiers first) is a deliberate, working mitigation. The residual risk is inherent to keyword search as a taxonomy-fallback strategy, not a coding error.

Recall ceiling: nothing today can find a company outside Explorium's index or its taxonomy vocabulary

High · Architectural limitation
app/providers/ — only Explorium and the mock declare COMPANY_DISCOVERY

Explorium is a structured, keyword/taxonomy-driven database. A genuinely obscure D2C brand with thin web presence, or one whose LinkedIn category doesn't match how a user phrases their ICP, is structurally invisible to the current pipeline regardless of qualification quality downstream — there's no semantic "find companies like this" capability anywhere in the code.

NAICS is documented but not live-verified

Medium · Needs live verification, not a code issue
providers/explorium.py — NAICS branch, per Phase 8B's own stated status

The precedence and caching logic are unit-tested against mocked responses; whether NAICS resolution behaves as expected against the real Explorium API has not been confirmed. This is explicitly flagged rather than assumed.

_DefaultMockProvider always returns GOOD_FIT. Any company that passes hard rules today is qualified by a stub, not a real judgment — meaning the false-positive problem currently has no semantic backstop at all downstream of discovery.

Strengths, weaknesses, and role — per provider

OpenAI API

reasoning layer, not a data source

Strength: Structured Outputs give a hard schema-conformance guarantee (never malformed JSON); function calling is a mature, low-risk fit for turning free-text ICP language into structured filter parameters; Batch API halves cost and runs on a separate rate-limit pool, making bulk classification of thousands of companies cost trivial (~$0.25–$3 per 10,000 companies).

Weakness: No company database and no ability to fetch a specific URL's content on its own unless web_search is used — structural conformance is guaranteed, factual correctness is not, and depends entirely on what evidence is in the prompt.

Best role: (a) ICP interpreter — natural language → structured discovery parameters; (b) cheap bulk-tier classifier over evidence someone else fetched, with a mandatory confidence field to escalate ambiguous cases.

Exa

semantic discovery + targeted verification

Strength: the only candidate with both a purpose-built company-search vertical (structured entity fields: headcount, funding, HQ, founded year) and genuine embeddings-based semantic matching, explicitly benchmarked against obscure/long-tail companies rather than famous ones. Contents + Answer with a steerable summary.query is well-suited to the D2C/agency verification question specifically, with cited, schema-constrained output.

Weakness: no numeric employee-count or hard geography pre-filter (expressed only as NL text in the query); bulk discovery at scale requires the separate Websets product with its own subscription pricing, not the pay-as-you-go Search API.

Best role: secondary semantic-discovery branch for recall on companies Explorium's taxonomy/keyword search structurally can't reach, and as the verification engine for ambiguous candidates.

Tavily

verification/enrichment utility

Strength: mature, well-documented Search→Extract→Crawl toolchain explicitly recommended by Tavily itself for due-diligence/enrichment use cases; full-page content extraction (not just snippets), with an "advanced" mode for tables; clean per-result citation URLs.

Weakness: no structured company database, no confirmed embeddings-based semantic search (its own docs describe "proprietary AI" reranking over live web results, not an explicit neural index — genuinely more ambiguous in its own documentation than Exa's positioning); no employee/industry filters; geography is a soft ranking boost only, not a hard filter; no bulk/batch endpoint.

Best role: a credit-efficient alternative or complement to Exa/Perplexity specifically for the "read this company's website" step of verification — narrower in scope than Exa (no company index of its own) but well-documented for exactly this sub-task.

Perplexity

high-evidence selective verification

Strength: genuine structured citations (per-claim URL annotations with character offsets, plus a full source list) — the strongest audit trail of any candidate; fetch_url + web_search in one orchestrated call is architecturally exactly the "read a specific company's site, corroborate with the wider web" pattern this verification step needs; structured JSON-schema output supported.

Weakness: no structured filters of any kind (no discovery capability); multi-second-to-tens-of-seconds latency per call; QPS caps at low spend tiers (1 QPS at Tier 0); meaningfully more expensive per call than Exa/Tavily for the same job.

Best role: a small, low-volume "second opinion with the strongest citation trail" tier for the genuinely hardest, highest-stakes ambiguous cases — not a default verification path for every borderline candidate.

People Data Labs

not recommended for this problem

Strength: larger raw company count than Explorium (70M+ claimed vs. Explorium's ~30M), native NAICS/SIC codes, mature bulk-enrichment endpoints, and by far the strongest person/contact-enrichment API of the five — genuinely complementary to Unipile/person discovery, just outside this audit's company-discovery scope.

Weakness — decisive for this problem: no natural-language query, no semantic search, no website-content reading, confirmed absent. It is architecturally the same category of tool as Explorium — structured taxonomy lookup — and reviewer commentary suggests its company-level data (as opposed to person data) is comparatively thin for smaller/obscure companies. It cannot answer "is this company actually D2C" any better than Explorium's own industry field already can, because it has no mechanism beyond the same class of categorical proxy.

Best role: none identified for company discovery or verification specifically. Its clearest value (person/contact enrichment) is out of this audit's stated scope and would need its own evaluation against Unipile.

Why each new component exists, specifically

  • OpenAI as ICP interpreter — solves "natural-language ICP understanding" directly, and only. It runs once per ICP submission, not once per candidate, so its cost is negligible regardless of batch size. It produces structured parameters that feed the existing query builder; it does not gain authority over discovery or qualification.
  • Exa as a bounded secondary discovery branch — solves the recall problem for companies outside Explorium's taxonomy vocabulary or index, using genuine semantic matching rather than another keyword search. Bounded explicitly: only invoked when the Explorium branches, after their existing pagination/branch-merge logic, haven't produced enough candidates against the requested target — mirroring the "under-delivery is expected, never forced" principle already in batch-contract.md, extended to mean "reach for the expensive branch only when the cheap one is insufficient," not "always run both."
  • Selective AI verification wired into the existing Phase 16 interface — solves the D2C/FMCG problem (Section 6) directly. It never runs on every candidate — only on candidates the deterministic hard-rule engine already marked HOLD, or PASS candidates whose only supporting industry evidence came from Explorium's keyword-fallback tier (a signal already present in evidence records today, since evidence_import.py already tags source/provider per record).

What this architecture deliberately does NOT do

It does not give any LLM output authority to override a hard-rule FAIL, does not replace Explorium as primary discovery, does not run any paid provider on every candidate, and does not introduce a new evidence taxonomy — everything routes through evidence-policy.md's existing SEARCH_RESULT/PROVIDER_API source types and quality-contract.md's existing hard/soft separation.

The funnel principle: each stage only processes what the previous stage couldn't resolve. Nothing expensive runs on every candidate.

Concrete worked example: a batch requesting 50 accepted companies, where Explorium alone discovers 60 raw candidates (typical over-discovery to survive attrition) and 12 of them land on HOLD or carry only keyword-fallback industry evidence: OpenAI runs once (ICP interpretation), Exa discovery runs zero times (target already met), and the verification stage runs on 12 candidates, not 60 — at roughly $1-$5 in Exa Contents+Answer cost per company (well under $50 total), with Perplexity/Tavily escalation touching perhaps 2-3 of the hardest cases at $0.01-0.03 each. The expensive providers never see the 48 candidates that were already unambiguous.

A hard per-batch budget ceiling for external providers is not currently defined anywhere in the codebase — batch-contract.md references "provider budget" as a concept but doesn't quantify one. This proposal treats defining that ceiling as part of the smallest first implementation (Section 7), not something to leave implicit.

6

The D2C/FMCG test

The failure mode: an ICP asks for "D2C/FMCG brands." Explorium's structured taxonomy has no exact label for that phrasing, so the term falls to website_keywords, which matches any site mentioning "D2C" or "FMCG" — surfacing marketing agencies and consultancies whose service pages describe working with D2C/FMCG clients, not companies that are one.

How this architecture prevents the false positive — without ICP-specific hardcoding

  1. Discovery still lets the agency through — this proposal doesn't change Explorium's discovery-time behavior, deliberately (Section 8: no architecture replacement). The agency still enters the candidate pool, exactly as today.
  2. Its evidence is honestly weak, by an existing mechanism. evidence_engine.py already only trusts a single Explorium sighting as SUPPORTED_STRUCTURED for industry and country specifically when it came from the structured tiers. A keyword-fallback-sourced industry match is exactly the kind of single, unstructured sighting this mechanism was built to treat cautiously — no new logic needed, only a way to tell (at the evidence-record level) which Explorium branch produced a given company, which is already implicit in which filter tier matched.
  3. The hard rule already can't rubber-stamp it. hard_rule_engine.py::_evaluate_choice_field does exact-string equality against the allowed industry list — "Marketing Agency" (the agency's real, evidenced industry, once any evidence exists for it) does not equal "D2C" or "FMCG," so it FAILs or HOLDs on its own, independent of anything new.
  4. Where it actually slips through today: when the agency's evidenced industry field itself gets set to something ambiguous or absent, e.g. Explorium returns a generic "Retail" or "Consumer Goods" naics_description that isn't specific enough for the exact-match rule to reject, and the candidate lands on HOLD rather than a clean FAIL. This is exactly the HOLD population the new verification stage targets — not a special D2C/FMCG rule, but the same generic "evidence didn't clear the bar, and there's a reachable-cost way to research further" case the Quality Contract already anticipates (§2, outcome 1: "HOLD the lead and schedule further research, if more evidence is plausibly obtainable").
  5. Verification asks the generic question, not a D2C-specific one. The prompt to Exa/Perplexity is never "is this a D2C company" — it's the same shape for every vertical: "does this company manufacture/sell its own products, or does it provide services to other companies in this space?" (a service-vs-principal distinction), with the ICP's specific industry terms passed as context, not hardcoded into branching logic. This generalizes to any ICP where the keyword-fallback tier risks conflating "mentions X" with "is X" — SaaS-for-healthcare vs. a healthcare provider, fintech-consulting vs. a fintech company, and so on — without a single ICP-specific code path.
  6. The verdict feeds back through the existing, not a new, gate. The verification call's structured output (service-vs-principal classification + confidence + cited evidence) becomes a new evidence record via the existing evidence pipeline, and the existing hard-rule/HOLD-resolution logic decides PASS/FAIL/HOLD from there — the LLM never directly emits PASS/FAIL/HOLD itself, per Phase 16's own already-built anti-fabrication design and per quality-contract.md's rule that hard rules are "never [evaluated] by an LLM."

Would it still find legitimate D2C companies?

Yes, by construction: a genuine D2C brand's own website reads as "we manufacture and sell our own products directly to consumers" — the same generic service-vs-principal question resolves the opposite way, with equally strong cited evidence, and the candidate proceeds to PASS rather than staying stuck on an unresolved HOLD. Nothing about this mechanism makes false negatives more likely than the current keyword-fallback-only system; it only adds a second opinion for the ambiguous middle, which today has no resolution mechanism beyond an indefinite HOLD.

7

Implementation plan — phased, not yet started

Ordered so each phase is independently shippable, testable, and reversible. Nothing here is implemented — this is sequencing only.

FIRST

Wire ONE real LLMProvider into the existing Phase 16 interface, gated to HOLD only, behind a feature flag

The smallest possible first step: implement a single new LLMProvider subclass (Exa- or OpenAI-backed) in llm_providers/, following the exact pattern default_registry.py's own docstring already describes. Route it only through the existing HOLD path, not PASS/FAIL. No discovery changes, no new evidence source types, no query-builder changes. Fully reversible via the existing dependency-override pattern already used in tests.

Why first: it's the one component with zero blast radius — it can only affect candidates already stuck at HOLD, which today have no automated resolution path at all, so there's no existing behavior to regress.

2

Define and enforce a quantified per-batch provider budget

Turn batch-contract.md's unquantified "provider budget" concept into an actual ceiling (e.g., max N verification calls per batch, hard-stop, reported honestly per the batch contract's existing metrics model) before any provider that costs real money per call is allowed to run unconditionally.

3

Tag evidence records by discovery branch/tier at the point of creation

A small addition to evidence_import.py so a company's industry evidence record carries whether it came from linkedin_category, naics_category, or the keyword-fallback tier — the signal the verification-routing logic in Section 4/6 needs to identify "PASS but only via weak evidence" candidates, not just HOLD ones.

4

OpenAI ICP interpreter, additive and optional

A new pre-discovery step that proposes structured filter parameters from free-text ICP input, shown to the user for confirmation before build_company_discovery_query runs — never silently overriding what a user typed into structured fields directly.

5

Bounded Exa semantic discovery branch, shortfall-triggered only

Added only after Phases 1-3 have real production signal on how often HOLD/weak-evidence verification actually resolves correctly — recall improvements are the highest-risk, highest-cost component and should be sequenced last, once the verification stage it depends on for quality control is already proven.

6

Escalation tier (Perplexity/Tavily) for low-confidence verification results

Only after Phase 1's default verification provider has enough real volume to show how often it self-reports low confidence — sized to actual need, not speculative.

Risk check

  • ✓Does not break existing discovery — Explorium's query construction, branch precedence, pagination, and dedup are untouched in every phase; the new discovery branch (Phase 5) is additive and shortfall-triggered, never a replacement.
  • ✓Does not remove Explorium — remains the sole primary discovery provider throughout; nothing in this proposal reduces its role.
  • ✓Does not redesign the whole architecture — the new verification stage reuses the existing Phase 16 LLMProvider interface exactly as designed; domain dedup reuses company_identity.py; evidence reuses the existing SEARCH_RESULT/PROVIDER_API source types. No new abstraction layer is proposed.
  • ✓Does not introduce unbounded API calls — every new external call is scoped: the ICP interpreter runs once per ICP; Exa discovery is shortfall-capped; verification runs only on HOLD/weak-evidence candidates with a proposed hard per-batch ceiling (Phase 2).
  • ✓Does not create ICP-specific hardcoding — the verification prompt asks a generic service-vs-principal question with ICP terms as context, not a D2C/FMCG-specific branch; the same mechanism generalizes to any industry where keyword fallback risks conflating "mentions X" with "is X."
  • ✓Does not weaken hard-rule authority — evaluate_hard_rules is not modified in any phase; the LLM never emits PASS/FAIL/HOLD directly, only evidence that feeds the existing deterministic engine, per quality-contract.md's explicit rule that hard rules are "never [evaluated] by an LLM, a score, or an aggregate confidence value."

Is this the right architecture, or just the user's hypothesis confirmed by default?

The hypothesis was directionally right but under-specified in two places this audit corrects: it named "Exa/etc." generically for the web/semantic branch, when the research shows Exa specifically (not Tavily, not Perplexity, not PDL) is the one candidate built for structured-plus-semantic company discovery — the others are verification-only tools, and PDL adds no real capability over Explorium for this problem at all. And it proposed the AI verification step as a new stage, when the codebase already contains a fully-designed, currently-inert slot for exactly that role (Phase 16's LLMProvider interface) — building a new stage instead of wiring the existing one would be the unnecessary architecture change Section 8 rules out.

The corrected recommendation: keep the funnel shape from the hypothesis, but implement it as wiring, not rebuilding — one new provider class behind an existing interface first, a quantified cost ceiling second, and the new discovery branch last, after the verification stage has proven itself on real HOLD candidates.
